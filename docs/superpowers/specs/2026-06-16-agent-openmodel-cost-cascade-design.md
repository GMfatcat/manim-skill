# Agent × 開源模型成本分工框架 — Contract-Gated Cascade

**日期**：2026-06-16
**狀態**：設計（brainstorming 產出，待實作計畫）
**參考實作**：`manim-skill` 本身就是此框架的縮影（agent 路徑 + backend 路徑、scene spec 契約、L0 確定性層、BeatRepairer）。

## 問題與情境

場內同時有**付費互動式 copilot**（IDE 內、人在迴圈）與**廠內免費開源模型**（vLLM/Ollama，<35B）。目標是讓兩者在**產物生成 pipeline**（concept → 驗證過的結構化產物，例如 manim-skill 的 spec/codegen/render）上合作，**首要驅動是成本**：付費 copilot 貴，要把大量、可容錯的粗活丟給免費本地模型，copilot 只做關鍵決策、品管、收尾。

### 約束（來自情境問答）

- **驅動力**：成本分工（最小化付費 copilot 用量），不以隱私/合規為主。
- **工作形狀**：產物生成 pipeline（concept → 驗證過的結構化產物），有強品質查核點。
- **編排方式**：互動式 copilot 為主、人在迴圈；copilot **不是** headless 總指揮。量產走 CLI，符合「整合走 CLI 不走 MCP」的既有偏好。

### 不在範圍

- 通用日常開發（改 bug / 審 PR）的分工——本框架專注產物生成 pipeline。
- 讓 copilot headless 自動跑批次的編排器。
- 把隱私/合規當主要驅動（容器沙箱仍保留，但不是設計目標）。

## 決策：方案 A — 契約優先 + 階梯升級（吸收「黃金範例」技巧）

把 copilot 的昂貴心力花在**可攤提、一次性**的契約與黃金範例上；量產的邊際成本壓到趨近 0；付費 copilot 的按量消耗只剩「升級硬骨頭」與「審核」，兩者都不隨產物數線性成長。

（評估過但未採用：方案 B「copilot 打樣、本地模型放大」——其黃金範例技巧被吸收進 A；方案 C「本地優先、copilot 當裁判」——copilot 永不生成，硬題沒人救，品質天花板 = 本地模型最好水準。）

## §1 角色與成本邊界

三層，依「每次呼叫的邊際成本」排序，貴的盡量少碰：

| 層 | 誰 | 邊際成本 | 職責 |
|---|---|---|---|
| **L0 確定性層** | 程式（schema 驗證、修復規則、模板、元件庫） | 0 | 擋結構性錯誤、保證版面/主題、吸收大半開源模型脆弱 |
| **L1 本地開源模型** | 廠內 vLLM/Ollama（<35B、免費） | ≈0（電費） | 跑量：批次生成、修復失敗的 raw 片段（黃金範例當 few-shot） |
| **L2 互動式 copilot + 人** | 付費 copilot（IDE 互動、人在迴圈） | 高 | ① 設計期定契約 + 黃金範例（一次性）② 升級期接 L0/L1 救不動的硬骨頭 + 關鍵審核點 |

**核心原則 — 成本邊界畫在「設計 vs 量產」，不是「難 vs 易」**：

- copilot 的錢花在**可攤提**的東西上（契約、黃金範例、修復規則），花一次惠及之後每個產物。
- 量產邊際成本趨近 0：每多一個產物，預設只動 L0+L1。
- L2 按量消耗只剩**升級**（受配額約束）+ **審核**（人本來就要做的決策），不隨產物數線性膨脹。

**契約是單一支點**：一份「驗證得過、結構化」的中介格式（manim-skill 的 scene spec / 元件庫即現成範例）。L2 定義它、L1 填充它、L0 驗證/修復它；三層只透過契約溝通，互不知彼此內部。

## §2 三個時期的資料流

因為 copilot 是互動式、人在迴圈，框架不讓 copilot 親自跑批次——而是人/copilot 在 IDE 下 CLI 指令，批次由免費本地模型背景跑，結果回到 copilot 眼前。

### ① 設計期（L2，一次性、花錢）

```
人 + copilot 互動 ──> 三樣可攤提資產（進版控）：
   ├─ 契約：schema / 元件庫 / 模板
   ├─ 黃金範例：copilot 親手寫的 2–3 個高品質產物
   └─ 修復規則：確定性 de-tox / repair_latex 類白名單（L0 用）
```

### ② 量產期（L0 + L1，按量、≈免費）— 一條 CLI 指令觸發

```
concept/輸入 ─CLI─> [L1 本地模型生成，黃金範例 few-shot]
                  ─> [L0 驗證] ──通過──> 產物
                        │失敗
                        └─> [L1 本地模型修復，最多 N 次] ──通過──> 產物
                                  │N 次仍失敗
                                  └─> 標記「待升級」，不阻塞其他項目
```

互動式 copilot 在這裡**不消耗 token**——只幫人把指令拼出來（如 `manim-skill bundle ... --repair --model <本地>`）。失敗項目被隔離、graceful degradation。

### ③ 審核 + 升級期（L2，少量、花錢）

```
量產結果回到 IDE ──> 人/copilot 看 manifest：
   ├─ 大多數：通過，直接收貨
   ├─ 審核點：人決定概念對不對（本來就要做的決策）
   └─ 「待升級」清單（量小）──> copilot 互動式接手：
            讀 traceback + 黃金範例 ──> 改契約或手寫該產物 ──> 回灌
```

**關鍵接縫**：互動式 copilot 與量產之間的介面就是 **CLI + 檔案**（concepts.json / spec_NN.json / manifest.json / output.zip）——人在 IDE 看得到改得動，copilot 讀得懂。硬骨頭若反覆出現同一類，回流到①**強化契約**（加元件 / 加修復白名單），讓它從此沉到 L0/L1——這是框架隨時間變便宜的飛輪。

## §3 升級階梯 + 黃金範例雙重用途

### 四個關卡（每關先確認能否在本層解決，不行才往上爬；爬升花錢就設上限）

```
輸入
 ├─[關卡1] L1 本地模型生成（黃金範例 few-shot）
 │        指標：能 parse + 通過 schema 驗證？
 ├─[關卡2] L0 確定性修復（de-tox、repair_latex 白名單、結構修正）— 免費、無限次
 ├─[關卡3] L1 本地模型修復（traceback + 黃金範例餵回，最多 N 次）— 即 BeatRepairer
 └─[關卡4] L2 升級：copilot/人接手（唯一花錢、有量上限）
```

### 可調且可量測的旋鈕（成本框架的命脈）

| 旋鈕 | 預設 | 意義 |
|---|---|---|
| `N`（L1 修復次數） | 3 | 超過就不讓本地模型空轉燒時間 |
| 升級預算（每批 L2 配額） | 例 ≤ 10% 產物 | 超過 → **停下示警**：契約有系統性缺口，該回①補契約而非逐一硬修 |
| 升級觸發條件 | parse/驗證/渲染連續失敗 | 只有「確定壞」才升級；模稜兩可不升級（省錢） |
| 粒度 | 單一 beat / 單一產物 | 升級只接壞掉的最小單位，不整批重做 |

**升級配額被打爆 = 訊號，不是失敗**。ORCA 實測：gemma 的長條圖反覆爛，與其每次升級給 copilot，不如回去補一個 `BarChart` 元件（L0），之後所有長條圖沉到免費層。配額把「該強化契約」自動浮上來。

### 黃金範例一物兩用

copilot 設計期親手寫的 2–3 個高品質產物，存版控（如 `examples/gold/*.json`）：

- **用途一 — L1 few-shot 範本（量產、免費）**：生成 prompt 帶 1–2 個最相近黃金範例，讓本地模型照抄結構。ORCA 啟示：nemotron 全 raw 才 59%，但看得到「用元件」的範例就更可能挑元件——範例比 prompt 規則更能釘住偏好。
- **用途二 — L2 升級參考（升級期）**：copilot 接硬骨頭時有「正確長相」可對照；發現未涵蓋的新模式就順手新增黃金範例（範例庫長大，下次該類沉到 L1）。

**維護成本控制**：黃金範例求**覆蓋產物類型**（每種主要 component/模板一個代表），不求多。挑選用現成「依概念類型取最近鄰」，不需訓練。

## §4 錯誤隔離 + 成本量測

### 錯誤隔離（沿用 manim-skill 既有、免費的韌性）

- **逐項隔離**：一個產物失敗不拖垮整批；升級只接最小壞單位。
- **Graceful degradation**：量產期永遠產出「能產的部分」+ `manifest`（哪些成、哪些待升級、各自原因）。人/copilot 看 manifest 決策。
- **沙箱**：L1 產的 raw 程式碼在容器內跑（`--network none`、唯讀、資源/逾時上限）——刻意讓不可信的免費模型大量產碼，沙箱在成本框架裡尤其重要。

### 量測（沒有指標就只是感覺）

每批跑完記結構化 metrics（manifest 延伸），核心是「工作在哪一層被解決」的分布：

| 指標 | 算法 | 健康訊號 |
|---|---|---|
| 層級解決分布 | 各產物最終在 L0/L1/L2 哪關收斂 | 絕大多數落 L0+L1（免費層）|
| 升級率 | L2 接手數 / 總產物數 | 低且 < 升級配額 |
| copilot token / 批 | L2 實際消耗 | 接近固定（不隨產物數線性成長）|
| 每關成功率 | 關卡1/3 通過率 | 對照基線，看契約強化有沒有把曲線往上推 |
| 省錢比 | (全走 copilot 估計成本) ÷ (實際 L2 成本) | 越高越好；對主管報告的數字 |

**驗證框架本身**：用既有 `scripts/eval/` 思路擴充，拿固定素材（如 ORCA）定期跑，盯「層級分布」與「升級率」隨契約演進的變化——飛輪有沒有在轉（硬骨頭逐步沉到免費層）一眼可見。

### ORCA baseline（第一筆量測資料）

| 來源 | beat 成功率 | 層級 | 備註 |
|---|---|---|---|
| Agent 路徑（手寫 component） | 15/15 (100%) | L2 一次性 | 上限參考 |
| nemotron-3-nano-30b（全 raw） | 10/17 (59%) → +repair 16/17 (94%) | L1 | 修復把 59%→94%，全程未動 L2 |
| gemma-4-31b（混合） | 25/31 (81%) → +repair 28/31 (90%) | L0+L1 | 殘餘失敗集中在長條圖 → 該補 `BarChart` 元件（典型「配額訊號 → 強化契約」案例）|
